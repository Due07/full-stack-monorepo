## 1. 项目目标与范围

### 1.1 一期必须交付
基于当前后端已实现接口，前端后台系统必须交付以下页面与能力：

1. 登录页
2. 登录态持久化
3. access token 自动携带
4. refresh token 自动刷新
5. 登录失效自动跳转登录页
6. 当前登录用户信息页
7. 当前会话信息页
8. 用户列表页
9. 用户详情页
10. 后台创建账号能力
11. 用户状态切换（启用 / 禁用）
12. 用户会话查看页
13. 用户登录历史查看页
14. 审计日志列表页
15. 冻结账号手动解封能力
16. 按角色控制菜单与页面访问
17. 基于 Swagger / 后端 DTO 的字段展示说明
18. 后台工作台中的“开放用户端注册”系统配置开关

### 1.2 一期明确不做
以下内容不进入本次实现：

- 微信相关页面与绑定管理
- 对外注册页面本身
- 找回密码 / 重置密码
- 短信验证码登录
- 多主题切换
- 多语言
- 图表大盘 / BI 报表
- 权限配置平台（例如角色配置界面、资源授权界面）
- 复杂筛选器（先保证主链路可用）

### 1.3 交付原则

- 优先保证功能闭环，不追求过度包装
- 严格以当前后端接口实际实现为准，不脑补不存在的字段
- 统一按后端返回格式 `{ code, msg, data }` 处理
- UI 使用 `ant-design`
- 样式使用 `unocss + scss`
- 状态管理使用 `zustand`
- 尽量少引入额外状态库，保持实现清晰直接

## 4. 后端接口清单（按当前实际实现）

以下接口必须作为前端唯一联调依据。

### 4.1 管理端认证接口

- `POST /api/admin/auth/login`
- `POST /api/admin/auth/refresh`
- `POST /api/admin/auth/logout`
- `GET /api/admin/auth/me`

### 4.2 管理端当前用户会话接口

- `GET /api/admin/sessions`
- `DELETE /api/admin/sessions/:sessionId`
- `POST /api/admin/sessions/logout-all`

### 4.3 管理员接口

- `GET /api/admin/users`
- `POST /api/admin/users`
- `GET /api/admin/users/:id`
- `PATCH /api/admin/users/:id/status`
- `POST /api/admin/users/:id/force-logout`
- `POST /api/admin/users/:id/force-logout-all`
- `POST /api/admin/users/unfreeze-login`
- `GET /api/admin/users/:id/sessions`
- `GET /api/admin/users/:id/login-history`
- `GET /api/admin/users/audit-logs/list`

### 4.4 系统配置接口

- `GET /api/admin/system-settings`
- `PATCH /api/admin/system-settings/:key`

### 4.5 用户端 H5 接口

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/register`

### 4.6 统一响应格式

成功响应：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

失败响应：

```json
{
  "code": 401,
  "msg": "密码错误",
  "data": {}
}
```

前端规则：

- 所有页面只消费 `data`
- `msg` 用于错误提示 / 成功提示
- `code !== 200` 时统一按错误流程处理
- `code` 必须视为数字类型，不使用字符串错误码

## 5. 后端核心业务规则（前端必须遵守）

### 5.1 登录规则

- 登录使用 `account + password`
- `account` 可为 `username` 或 `phone`
- 登录页不展示注册入口
- 登录失败时前端直接显示后端返回 `msg`
- 密码错误提示统一为：`密码错误`
- 账号禁用提示统一为：`该账号已被禁用`

### 5.2 注册规则

虽然后台本身不提供对外注册页面，但前端理解接口时要知道：

- 用户端登录与注册走独立前缀：`/api/v1/auth/*`
- 注册只允许创建 `user`
- 登录允许 `user / admin / superAdmin`
- `displayName` 是外显名称
- `username` 注册后不可修改
- 无 email 体系
- `phone` 默认非必填
- 用户端 H5 注册入口是否开放由 `system_settings.public_user_register_enabled` 控制
- `phone` 是否要求必填仍可受环境变量控制

### 5.3 用户端注册开关规则

- 用户端注册入口受系统配置控制
- 配置表：`system_settings`
- 配置键：`public_user_register_enabled`
- 默认值：`false`
- 配置入口：后台工作台
- 可操作角色：`admin / superAdmin`
- `user` 不可见该开关

### 5.4 Token 规则

- access token 默认 `24h`
- refresh token 默认 `7d`
- refresh 通过管理端接口 `POST /api/admin/auth/refresh`
- refresh 失败时，前端必须清空登录态并重新登录

### 5.5 单登录与会话规则

- 后端最终规则是：**不允许多端同时登录**
- 同一用户同一时刻只存在一个有效会话
- 因此前端不需要实现复杂的“多设备在线管理”
- 当前用户会话页本质上是“当前唯一有效会话信息展示”
- 管理端强制下线仍保留，因为管理员可以让目标用户当前会话立即失效

### 5.6 角色规则

后台角色：

- `superAdmin`
- `admin`
- `user`

前端权限边界：

- `superAdmin`：显示全部后台菜单，可访问全部后台能力
- `admin`：可访问用户管理相关页面，不可访问审计日志，不可管理 `superAdmin`
- `user`：不进入后台管理主页，仅可使用个人相关能力

### 5.7 冻结 / 解封规则

- 登录失败按 `account` 维度冻结
- 默认规则：24 小时内连续失败 10 次触发冻结
- 冻结提示直接显示后端原文
- 后台支持手动解封：`POST /api/admin/users/unfreeze-login`
- 解封时 `reason` 可为空

### 5.8 审计与登录历史规则

- 登录成功 / 失败会进入日志
- 管理员关键操作会进入日志
- 审计日志保留 `7d`
- 登录历史保留 `15d`
- 前端不负责清理数据，只负责按实际含义展示

## 7. 页面说明

### 7.1 登录页

职责：

- 输入 `account` 与 `password`
- 进行前端基础校验

- 登录成功后写入本地登录态

校验要求：

- 登录按钮必须有 loading

职责：

- 作为后台首页

- 切换时展示 loading 和结果提示

### 7.3 我的信息页

职责：

- 展示当前登录用户基本信息
- 展示当前会话信息：设备、IP、UA、最后活跃时间、过期时间
- 提供退出登录入口
- 提供“全部下线”入口

### 7.4 用户管理页

职责：

- 分页展示用户列表
- 支持创建账号
- 支持查看详情
- 支持启用 / 禁用

规则：

- `admin / superAdmin` 可进入
- `admin` 只能创建 `user`
- `superAdmin` 可创建 `user / admin`

### 7.5 用户详情页

职责：

- 展示用户基础信息
- 展示最近登录时间和当前是否在线
- 提供“查看会话”“查看登录历史”入口
- 提供启用 / 禁用
- 提供强制下线

规则：

- 提供“返回列表”按钮
- 标题旁提供刷新按钮
- `admin` 查看 `superAdmin` 详情时直接进入 `403`

### 7.6 用户会话页

职责：

- 展示目标用户当前会话信息
- 支持执行强制下线

字段：

- `sessionId`
- `deviceType`
- `deviceName`
- `clientIp`
- `userAgent`
- `lastActiveAt`
- `expiresAt`
- `isRevoked`

规则：

- 提供“返回详情”按钮
- 标题旁提供刷新按钮

### 7.7 用户登录历史页

职责：

- 展示目标用户登录成功 / 失败历史
- 支持分页

展示要求：

- `action` 中文映射
- `action` 颜色区分
- `metadata` 直接按 JSON 字符串展示

规则：

- 提供“返回详情”按钮
- 标题旁提供刷新按钮

### 7.8 审计日志页

职责：

- 展示系统审计日志

展示要求：

- 分页
- `action` 中文映射

- `metadata` 直接展示

## 9. 请求层实现要求

### 9.1 本地存储内容

本地至少存：

- `accessToken`
- `refreshToken`
- `currentUser`

### 9.2 请求函数行为

统一请求封装必须满足：

1. 自动携带 `accessToken`
2. refresh 请求时，自动把 `refreshToken` 放到后端需要的位置
3. 成功响应自动返回 `data`
4. `code !== 200` 时抛出业务错误
5. 401 / refresh 失败时：
   - 清空本地登录态
   - 跳转 `/login`
6. 所有错误统一走消息提示

### 9.3 refresh 策略

- access token 失效后自动 refresh 一次
- refresh 成功则重放当前请求
- refresh 失败则退出登录
- 并发 refresh 需要单次刷新锁，避免多个请求同时刷新

### 9.4 服务层建议

按职责拆分 service：

- `services/auth.ts`
- `services/sessions.ts`
- `services/admin-users.ts`
- `services/system-settings.ts`
- `services/request.ts`

## 10. 权限与页面守卫要求

### 10.1 登录态守卫

- 未登录访问后台路由：跳 `/login`
- 登录后刷新页面，应能恢复登录态并重新获取当前用户信息

### 10.2 角色守卫

- `superAdmin`：可访问全部后台页面
- `admin`：
  - 可访问 `/users`
  - 可访问 `/users/:id`
  - 可访问 `/users/:id/sessions`
  - 可访问 `/users/:id/login-history`
  - 不可访问 `/audit-logs`
- `user`：
  - 不可访问后台管理页面
  - 仅允许进入 `/profile` 或被重定向离开后台

### 10.3 无权限体验

不要直接白屏，必须提供：

- 标准 `403` 页面
- 可返回的明确入口

刷新要求：

- 复用页面已有 loading 状态
- `PageCard` 或对应卡片显示 loading

### 11.4 返回按钮

必须提供：

## 15. 开发时必须避免的误区

1. 不要在后台登录页暴露用户端注册入口
2. 不要做 email 登录
3. 不要做复杂多设备管理交互
4. 不要假设 `admin` 可以管理所有角色
5. 不要让 `admin` 看到审计日志页
6. 不要让 `user` 进入后台主页
7. 不要把后端字段自行改名后到处兼容
8. 不要把样式全部写成内联样式
9. 不要继续沿用旧接口前缀 `/auth/*`、`/sessions/*`

---

## 16. 最终输出物

开发完成后，至少应产出：

1. 可运行的后台页面代码
2. 完整路由与布局结构
3. 请求层与鉴权处理
4. 与后端接口对应的 service 层
5. 共享组件（`RoleTag / StatusTag / PageCard`）
6. 样式文件（`UnoCSS + SCSS`）
7. 一份可用于联调和回归的检查清单

---

## 17. 结论

这份计划的定位不是“思路说明”，而是“实施规范”。

如果交给另一个没有上下文的开发者，要求他：

- 先搭后台骨架
- 再接登录主链路
- 再按页面逐步实现
- 严格对齐后端接口和规则

那么应该可以直接按照本计划落地，不需要再额外追问大量上下文。
