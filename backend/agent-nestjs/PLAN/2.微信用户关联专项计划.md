# 微信用户关联专项计划

- 生成日期：2026-04-24
- 适用服务：`backend/agent-nestjs`
- 文档目标：将“微信身份绑定”从主登录系统中拆开，形成可独立实施的专项计划，避免与本地登录体系耦合。
- 此计划先暂停！等待后续再接入！！！！！！！！！
- 当前明确前提：
  - 本专项依赖主计划中的用户体系、JWT 鉴权、审计日志能力已存在
  - 当前只规划“已登录用户绑定微信身份”，不做完整微信直登闭环

## 1. 范围定义

### 1.1 本专项必须完成
- 已登录用户绑定微信身份
- 当前用户查看自己的微信绑定列表
- 当前用户解绑自己的微信身份
- 绑定 / 解绑动作审计
- 为未来微信直接登录预留统一身份模型

### 1.2 本专项不做
- 微信直接登录
- 微信授权登录 UI 流程设计
- 企业微信集成
- 多微信生态同时完整落地

## 2. 待确认输入

正式开发前，必须确认以下业务信息：
- 接入的是：`微信小程序`、`微信公众号网页授权`、`微信开放平台网站应用` 中哪一种
- 前端目前如何获得授权 `code`
- 是否能稳定获取 `unionid`
- 是否允许一个系统用户绑定多个微信身份

如果以上信息未确认，本专项只能先完成数据结构和接口壳子，不能直接进入正式联调。

## 3. 设计原则

- 微信绑定必须建立在“系统用户已登录”的前提下
- 微信身份是第三方身份映射，不应反向污染本地认证主链路
- `openid` 只在特定平台上下文内可靠
- 若能获取 `unionid`，优先将其视为跨平台归并辅助字段
- 敏感凭证不写明文日志

## 4. 数据模型设计

### 4.1 `wx_accounts`
建议字段：
- `id`
- `user_id`
- `platform`
- `openid`
- `unionid`
- `nickname`
- `avatar_url`
- `raw_profile`
- `created_at`
- `updated_at`

约束建议：
- `platform + openid` 唯一
- `unionid` 建索引
- `user_id` 建索引

字段说明：
- `platform`：标识微信来源，例如 `miniapp` / `oa-web` / `open-web`
- `raw_profile`：仅保存最小必要原始数据，便于排障；不要长期保存敏感 token

## 5. 绑定规则

### 5.1 核心规则
- 用户必须先登录本系统
- 一个微信身份只能绑定一个系统用户
- 一个系统用户可以绑定多个微信身份
- 同一用户重复绑定相同身份时，返回已绑定结果而不是重复插入

### 5.2 冲突规则
- 若该微信身份已绑定其他用户，返回冲突错误
- 若传入平台与身份信息不匹配，返回参数错误
- 若微信侧未返回关键身份字段，返回第三方身份解析失败

### 5.3 解绑规则
- 允许用户解绑自己的微信身份
- 若后续支持微信直登，则解绑前需要校验是否仍有其他可登录方式
- 管理员代解绑应单独走管理接口并写审计日志

## 6. 模块设计

建议新增：
- `src/modules/wx-accounts`
- `src/modules/wx-providers`（可选但推荐）

### 6.1 `wx-accounts`
- 对外提供绑定、解绑、查询接口
- 负责数据库存取与唯一性校验
- 负责绑定结果脱敏展示

### 6.2 `wx-providers`
- 根据平台类型调用不同微信接口
- 将微信返回结果统一归一为内部身份对象
- 隔离第三方平台差异，避免业务 service 直接堆砌条件判断

## 7. API 设计

### 7.1 用户侧接口
- `POST /wx/bind`
- `POST /wx/unbind`
- `GET /wx/bindings`

### 7.2 管理侧接口（可选二期）
- `GET /admin/users/:id/wx-bindings`
- `DELETE /admin/users/:id/wx-bindings/:bindingId`

### 7.3 响应约定
建议复用主计划的统一响应结构：
- 成功：`{ code, message, data }`
- 失败：`{ code, message, error, details? }`

建议错误码：
- `WX_PLATFORM_UNSUPPORTED`
- `WX_IDENTITY_RESOLVE_FAILED`
- `WX_ACCOUNT_ALREADY_BOUND`
- `WX_BINDING_NOT_FOUND`
- `WX_BINDING_CONFLICT`

## 10. 绑定流程设计

### 10.1 标准绑定流程
- 前端发起微信授权
- 前端获得 `code`
- 前端调用 `POST /wx/bind`
- 后端按 `platform` 调用 provider 解析微信身份
- 后端检查该身份是否已被其他用户占用
- 未占用则建立 `wx_accounts` 记录
- 记录审计日志并返回绑定结果

### 10.2 查询流程
- 已登录用户请求 `GET /wx/bindings`
- 后端按当前用户 ID 查询并返回脱敏结果

### 10.3 解绑流程
- 已登录用户请求 `POST /wx/unbind`
- 后端校验 `bindingId` 归属
- 删除或逻辑解绑记录
- 写审计日志

## 11. 安全要求

- 微信密钥与 app secret 必须走环境变量
- 不记录明文 `openid`、`unionid`、微信 access token
- 若使用 `state`，则必须做校验
- 绑定与解绑接口建议做基础限流
- 查询接口返回必须脱敏

## 12. 环境变量建议

按具体平台再细化，至少会需要：
- `WX_APP_ID`
- `WX_APP_SECRET`
- `WX_OA_APP_ID` / `WX_OPEN_APP_ID` / `WX_MINIAPP_APP_ID`（按实际平台选）
- `WX_OA_APP_SECRET` / `WX_OPEN_APP_SECRET` / `WX_MINIAPP_APP_SECRET`

## 13. 测试建议

至少覆盖：
- 绑定成功
- 重复绑定同一身份
- 已被其他用户占用时绑定失败
- 查询绑定列表
- 解绑成功
- 解绑不存在记录失败
- 未登录调用绑定接口失败

## 14. 实施顺序

### 阶段 1：数据层与接口壳子
- 新增 `wx_accounts` 表

### 阶段 2：Provider 抽象

## 16. 已知风险与限制

- 微信生态差异会直接影响 provider 实现
- 如果拿不到 `unionid`，后续跨平台统一账号需要额外设计
- 不建议将“微信绑定”与“微信直接登录”在一期同时混合落地
