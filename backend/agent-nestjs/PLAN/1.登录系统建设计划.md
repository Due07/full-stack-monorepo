# 登录系统建设计划

- 生成日期：2026-04-24
- 适用服务：`backend/agent-nestjs`
- 文档目标：作为一期登录系统实施蓝图使用，要求新接手的开发者在没有额外聊天上下文的情况下，也能据此完成设计与开发。
- 当前明确前提：
  - 现有仓库技术栈为 `NestJS + TypeScript`
  - 当前仓库中的微服务能力和 agent 发送逻辑视为 demo，本计划不纳入改造范围
  - 微信关联能力单独拆到 `2.微信用户关联专项计划.md`

## 1. 一期范围定义

### 1.1 目标
一期必须交付以下能力：
- 用户注册
- 用户登录
- 获取当前登录用户信息
- refresh token 刷新 access token
- 当前用户查看自己的当前登录会话
- 当前用户退出当前会话
- 管理员禁用 / 启用用户
- 管理员强制用户下线
- 管理员解封因频繁登录被冻结的账号
- 提供完整 Swagger / OpenAPI 文档

### 1.2 非目标
一期不做：
- 微信直接登录
- SSO / OAuth 平台统一登录
- 复杂权限中心（ACL / ABAC）
- 短信验证码登录
- 邮件验证 / 找回密码
- 演示用微服务链路治理

### 1.3 成功标准
如果一期完成，应该满足：
- 新用户可完成注册并登录
- 登录后可以拿到 `accessToken` 与 `refreshToken`
- 过期的 `accessToken` 可通过 `refreshToken` 刷新
- 用户可看到自己当前唯一有效会话的设备信息
- 用户可执行“全部下线”，使当前唯一有效会话失效
- 管理员可禁用用户，并立即使其现有登录态失效
- 登录账号连续失败达到阈值后，会被冻结并在指定时间自动恢复；后台支持手动解封
- 所有接口可通过 Swagger 查看和联调

## 2. 架构与技术选型

### 2.1 数据库
- 选型：`PostgreSQL`
- 作用：存储用户、会话、角色、审计日志、第三方身份映射
- 选择原因：
  - 关系约束明确，适合账户体系
  - 支持事务和唯一约束
  - 后续扩展管理后台和统计能力更自然

### 2.2 ORM
- 选型：`Prisma`
- 作用：schema 管理、migration、类型生成、数据库访问
- 选择原因：
  - 对 NestJS 项目接入成本低
  - 迁移流程清晰
  - 类型提示完整，适合长期维护

### 2.3 缓存 / 会话控制
- 选型：`Redis`
- 作用：
  - refresh token 会话控制
  - access token 撤销辅助
  - token version 缓存
  - 登录限流 / 冻结控制
- 选择原因：
  - 适合短期安全态数据
  - 支持高频读写

### 2.4 API 文档
- 选型：`Swagger / OpenAPI`
- 作用：接口文档、自描述 DTO、联调、鉴权说明

### 2.5 认证体系
- 选型：`JWT access token + refresh token`
- 设计要求：
  - `accessToken` 默认有效期 `24h`，并支持环境变量动态配置
  - `refreshToken` 默认有效期 `7d`，并支持环境变量动态配置
  - refresh token 只保存 hash，不保存明文
  - refresh token 必须轮换

### 2.6 密码存储
- 选型：`Argon2`
- 说明：
  - 仅用于密码哈希
  - 不使用 AES / RSA 存储用户密码

## 5. Token 与会话设计

### 5.1 access token 载荷建议
建议最少包含：
- `sub`：用户 ID
- `sessionId`
- `role`
- `tokenVersion`
- `jti`

### 5.2 refresh token 设计
- 每次登录生成新的 `sessionId`
- 每个 `sessionId` 对应一个 refresh token
- refresh token 存库前做 hash
- refresh token 刷新时必须轮换并使旧值失效

### 5.3 强制下线策略
必须支持：
- 用户自己登出当前设备
- 用户自己踢指定设备
- 用户自己全部下线
- 管理员踢指定用户全部设备

推荐实现：
- 数据库将对应 `user_sessions.is_revoked = true`
- Redis 删除对应 `auth:refresh:{sessionId}`
- 用户全部下线时，将 `users.token_version + 1`
- JWT guard 校验 token 中的 `tokenVersion`

## 6. Redis Key 约定

建议统一 key：
- `auth:refresh:{sessionId}`
- `auth:user-sessions:{userId}`
- `auth:user-token-version:{userId}`
- `auth:blacklist:access:{jti}`
- `auth:rate-limit:login:{identifier}`

说明：
- 一期可优先落地 refresh 和 token version
- access token 黑名单作为可选增强，不是一期阻塞项

### 7.4 响应约定

推荐错误码分类：

- `AUTH_TOKEN_EXPIRED`
- `AUTH_TOKEN_REVOKED`
- `AUTH_USER_DISABLED`
- `AUTH_REFRESH_INVALID`
- `USER_ALREADY_EXISTS`
- `USER_NOT_FOUND`
- `SESSION_NOT_FOUND`
- `FORBIDDEN`

## 10. 权限与鉴权规则

### 10.1 角色
一期只保留：
- `user`
- `admin`

### 10.2 Guard 规则
- `/auth/register`、`/auth/login`、`/auth/refresh`：匿名可访问
- `/auth/me`、`/sessions/*`：登录用户可访问
- `/admin/*`：仅管理员可访问

### 10.3 用户状态控制
- `disabled` 用户禁止登录
- `disabled` 用户已有 token 失效
- 管理员不能禁用自己时，可作为二期约束；一期视业务需要决定是否实现

## 16. 已知决策与限制

- 当前计划默认采用前后端分离 API 模式，不做服务端 session 页面登录
- 当前计划默认 access token 走 Bearer Header
- 当前计划默认 refresh token 通过接口 Header 传递，不走 body 与 httpOnly cookie
- 当前计划默认登录仅支持 `username` 或 `phone`
- 当前计划默认不允许多端同时登录，新登录可使旧登录态失效
- 当前计划默认禁用用户后立即全部下线
- 当前计划默认管理员不允许禁用自己
